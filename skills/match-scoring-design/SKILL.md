# Match Scoring Design

一套「简历 × 岗位打分」的可信设计：100 分怎么拆、哪些交给模型哪些必须交给代码、
未知值怎么处理、怎么用零成本手段验证红线真的生效。适用于任何「给某物打分且要能解释」的场景
（简历筛选、供应商评估、合同要素核对）。

不做什么：不含具体业务字段与阈值调参；不含 UI；不讨论模型选型（只用得上 embedding + chat）。

## When to Use

- 要设计一个「分数必须能解释、能被追问」的评估系统
- 已有模型打分的原型，但客户/面试官问「为什么是 78 分」时答不出来
- 要判断某个环节该用规则还是该用模型

**Don't use for：** 纯排序场景（有监督标签、只要 AUC）、一次性人工评审、无需解释的内部实验。

## The Six Decisions

每条都给出**反例**与**本仓库实现位置**，照着做能在代码里找到对应落点。

### 1. 总分必须拆成加权分项（100 = 40 + 30 + 30）

- **反例**：让模型直接输出 0-100。分数不可解释，同一简历两次跑差 10 分也说不清原因。
- **做法**：硬性条件(规则) + 语义相近(本地模型) + 复核(LLM)，三段独立、各自可测。
- **落点**：`app/match_report.py::build_report`（total 只做三项相加）

### 2. 纯规则子项排在模型子项之前

- **反例**：先接 LLM 再补规则。模型分数飘的时候，你分不清是模型的锅还是汇总的锅。
- **做法**：先用零成本零不确定性的规则部分把链路测通（年限/学历/技能命中），再上模型。
- **落点**：`app/scoring_rules.py`（零 await、零网络），先于 `app/scoring_llm.py`

### 3. 「未知」永远不等于「不合格」

- **反例**：简历没写工作年限 → 抽取返回 0 → 硬性分判 0 → 一份资深简历被判不匹配。
- **做法**：未知单独成类型（`years_unknown` / `education_unknown`），扣分照扣但**类型不同**，
  报告里印 `?` 而不是 `✗`，并让整体状态降级为 `needs_review`。
- **落点**：`app/scoring_rules.py`（两种 type）、`app/report_pdf.py`（四态符号 ✓ ✗ ? —）

### 4. 相似度分两段：向量粗筛 + 交叉编码器精判

- **反例**：只用向量余弦。实测「负责分布式数据库内核开发」对 Go 订单简历拿 0.711，
  真相关项才 0.785 —— 中文技术句句式相同，小向量模型分不开领域。
- **做法**：余弦取 top-3 候选句 → cross-encoder 重排 → `covered = 重排分 >= 0`；
  余弦只给「有多像」的幅度。
- **落点**：`app/scoring_semantic.py`（`RERANK_THRESHOLD=0.0`，实测真相关 +5.53、无关 -0.86~-1.70）

### 5. 覆盖率必须进分母

- **反例**：`score = 30 × mean(已覆盖项相似度)` → 6 条职责只对上 1 条也能拿 22/30。
- **做法**：`score = 30 × Σ(已覆盖余弦) / 职责总数`，未覆盖按 0 进分母。
- **落点**：`app/scoring_semantic.py::score_semantic`

### 6. 证据不可编造，空证据直接失败

- **反例**：要求模型「给 reason」，它写得头头是道，但引用的 JD 原文根本不存在。
- **做法**：每个子项必须有 `jd_evidence` + `resume_evidence`；<4 字 → `failed`；
  原文里查不到 → 降级 `needs_review` 并记录字段名；建议里出现简历/JD 都没有的技术名 → 丢弃。
- **落点**：`app/scoring_llm.py::_validate_items` / `filter_suggestions`

## 怎么零成本验证红线真的生效

规则和护栏最容易「写了但没走过」。用假模型把异常路径走一遍，不花一分钱：

```python
# 1) 替换模型调用，返回构造好的 JSON（含空证据 / 越界分数 / 编造建议）
M.call_with_fallback_async = fake_call
# 2) 断言红线：空证据 → status=failed 且 score=0
# 3) 断言「模型不能决定档位」：模型自报 total=100、三项和 10 → 实际必须 10
```

**反例**：只用真实模型跑一遍就宣布通过 —— 正常输入永远走不到护栏分支，等于没测。

## 每块交付必须写「解决了什么」

不是「新增了 X 文件」，而是「消除了哪类风险 + 不做会怎样」。

- **反例**：「新增 pdf_font.py，注册了 4 级回退」
- **正例**：「消除 PDF 中文变方块的风险；不解决的话 S7 排完版才发现，整个报告要重做」

## Pitfalls

1. **阈值来源要能说清**。0.6 / 0.0 / 85 这些数字必须能指到实测或需求，否则一律算魔法数。
2. **中文句相似度普遍偏高**。同领域无关句常落在 0.55-0.75，别用 0.8 这种直觉阈值。
3. **`round(2.5)==2`**。Python 银行家舍入会让「扣分合计 ≠ 满分 - 得分」，统一用 `int(x+0.5)`。
4. **确定性 ≠ 模型确定性**。温度固定为 0 也只是「波动小」；要如实记录实测波动，不许宣称「完全一致」。
5. **别把「覆盖率低但一句很像」当高分**。这是最容易骗过自己的一类假阳性。

## Verification

- 每个子项都能独立回答「这项满分多少、为什么扣这个分、依据原文是哪句」
- 构造一条「无关简历 × 目标岗位」：语义分应接近 0，而不是 14-21 分
- 构造一条「简历没写年限」：类型是 `years_unknown`，报告印 `?`
- 假模型验红线的脚本能跑通且成本 0 元
