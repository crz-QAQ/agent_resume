## 一、功能定义

### 1.1 一句话

给一份简历 + 一个岗位（JD 文本，或只给岗位名称），输出：

1. **修改意见 PDF**：每条都写清「改哪里 / 为什么改 / 改成什么 / 改完有什么好处」
2. **智能修改（可选）**：按意见直接生成修改后的简历（docx）+ 逐条对比表

### 1.2 输入 / 输出

| 项 | 内容 |
|---|---|
| 输入 1 | 简历文件（PDF / docx，与评分功能同一入口）|
| 输入 2 | **岗位名称（必填）** —— 如「Java 后端开发工程师」|
| 输入 3 | **岗位 JD 文本（选填）** —— 有则按真实 JD 分析；无则按岗位名生成画像 |
| 输出 1 | JSON（`RevisionReport`，供程序消费）|
| 输出 2 | **修改意见 PDF**（**必出**，给人看、能转发）|
| 输出 3 | **修改后的简历**（仅「智能修改」时生成）<br>**格式跟随输入**（v1.3）：docx 进 → **docx 出（保留原版式）**；PDF 进 → PDF 出（重排，明确告知）|
| 输出 4 | **修改说明**（v1.3：从简历末页移出，放进意见报告 PDF 的「智能修改」章节 + JSON，保持简历文件干净可直接投）|

> v1.1 变更：岗位**名称必填，JD 选填**。理由：用户手里常常只有一个岗位名（面试邀请里就一行 title），
> 强制要 JD 会直接挡住一半使用场景；但有 JD 时必须优先用真实 JD（准确性优先）。
>
> v1.2 变更：**智能修改不是「替代」意见报告，而是「叠加」** —— 交付物 = ① 修改意见报告 + ② 修改后的简历。
> 缺任何一份都算未完成：只给改后简历 = 用户不知道改了什么、为什么改，等于黑箱。
>
> v1.3 变更：**简历版式尽量与用户上传的保持一致**。
> docx 输入走「原地替换段落文字」→ 字体/字号/加粗/表格/图片/页边距全部保留；
> PDF 输入无法保留版式（PDF 不可编辑），只能重排，必须在报告里明确告知并建议上传 Word 版。
> 同时把「本次修改说明」从简历文件里移出（否则会污染用户的简历版式），放进意见报告 PDF。

### 1.3 与已有功能的关系

```
评分功能（已有）：回答「配不配」
本功能（新增）  ：回答「怎么改」—— 建议基于评分结果中已暴露的问题，不另起一套判断
面试问答（未来）：回答「会被怎么问」
→ 三者共用同一份 ResumeInfo / JobInfo / 打分结果，不重复调用模型
```

### 1.4 明确不做（v1）

```
✗ 不编造经历、项目、公司、技能（见 §二 红线，这是本功能的生死线）
✗ 不做「一键伪造量化数字」（原简历没有的数字不许出现）
✗ 不做求职信 / 自我介绍
✗ 不做多语言简历翻译
✗ 不做 OCR（扫描件仍拒绝）
✗ 不做在线编辑器（生成 docx 让用户自己改）
```

## 二、红线（**比评分功能更严，违反即失败**）

```
① 不许新增「原简历 + JD」里都不存在的名词
   落地：改写后抽出的技术名/公司名/学校名 → 必须在 {原简历文本 ∪ JD 文本 ∪ 通用停用词} 里，
        否则该条改写作废，并记入 rejected_edits
② 不许改变量级或篡改数字
   落地：改写后出现的数字必须在原简历文本里能找到；找不到 → 作废
        （允许把「两秒」写成「2 秒」这种同一数字的写法变化）
③ 不许把「没有」写成「有」
   落地：JD 要求但简历完全没体现的能力，只能进「缺口/建议补充」，
        且必须带一句「如确有相关经历请补充，否则不建议写」
④ 每条意见必须能指到简历原句
   落地：original_text 在简历原文里能被检索到（去空白后子串）；找不到 → 丢弃
⑤ 岗位名推测的要求必须标注来源
   落地：JobProfile.source = "user_jd" | "inferred"；inferred 必须在 PDF 与 JSON 里明确标注，
        且必须经用户确认后才用于生成意见
⑥ 预估提分只能给「可确定性重算」的部分
   落地：硬性 40 + 语义 30 可重算 → 给具体数字；LLM 30 标「预估，波动 ±2」
```

## 三、修改意见的生成规则

### 3.1 问题分类（五类，代码枚举，模型只能选不能自创）

| code | 中文 | 含义 | 典型证据 |
|---|---|---|---|
| `missing` | 缺失项 | JD 要求、简历完全没体现 | JD 职责/必备技能未命中 |
| `weak_evidence` | 表达太弱 | 有事实但没量化/没结果/没规模 | 「负责后端开发」无规模无结果 |
| `buried` | 重点埋没 | 能力在，但位置靠后或不突出 | JD 核心要求出现在最后一段 |
| `noise` | 无关冗余 | 与目标岗位无关、占版面 | 与 JD 无关的证书/兴趣/旧项目 |
| `inconsistent` | 前后不一致 | 时间/职位/技能自相矛盾 | 年限与经历时间段冲突、「至今」歧义 |

### 3.2 每条意见必须包含**四段 + 两证据**（PDF 与 JSON 都按此结构）

```json
{
  "id": "R-003",
  "category": "weak_evidence",
  "severity": "high",
  "location": "工作经历 · 第 2 段",
  "original_text": "负责订单系统的接口开发",
  "suggested_text": "负责订单系统核心接口开发，支撑日均 XX 万级下单请求",
  "why": "JD 明确要求「高并发订单系统经验」，而这里只写了职责、没写规模与结果，招聘方无法判断量级",
  "gain": "让「订单系统」这条从「无法判断」变成「可验证的规模」，直接对应 JD 第 2 条职责",
  "jd_evidence": "负责订单系统接口开发与性能优化（JD 原文）",
  "risk_note": "「日均 XX 万级」必须是你真实数据；没有就改成你真实能说的数字"
}
```

- `why` 回答「为什么改」：必须引用 JD 的哪一条 + 简历的什么毛病
- `gain` 回答「改完有什么好处」：必须写「改前状态 → 改后状态」的具体对比，
  ✗ 不许写「更专业」「更有竞争力」这类空话
- `risk_note` 是**诚实兜底**：凡涉及数字/规模/成果的建议，必须提醒「只能是真实数据」

### 3.3 意见条数与排序

```
· 最多 12 条（超过就要用户自己挑重点，PDF 也放不下）
· 排序：severity(high→low) → category 优先级(missing > weak_evidence > buried > inconsistent > noise)
· high 最多 5 条；同一段经历最多 2 条建议（避免把一段话拆成 5 条流水账）
```

## 四、智能修改（可选动作）

### 4.1 输入输出（v1.3：两份产出 + 格式跟随输入）

```
输入：ResumeInfo + JobInfo（真实 JD 或岗位画像）+ RevisionReport（上一步的意见）+ 用户勾选的 issue_ids
输出（两份，缺一不算完成）：
  ① 修改意见 PDF   —— 复用 M4 的渲染；「智能修改」章节列出逐条 before/after + 未采用项
  ② 修改后的简历   —— 格式跟随输入：
       · docx 入 → `<原名>_修改版.docx`（**保留原版式**，见 §4.4）
       · pdf  入 → `<原名>_修改版.pdf`（重排单栏，报告里须告知版式已重排）
     ⚠️ 修改说明不写进简历文件（会污染版式），只放在 ① 与 JSON
```

> **v1.1 决定：v1 只出 PDF**（用户选择）。代价必须写进文档：
> PDF 不可继续编辑，用户若还想手改，需要 v2 的 docx 输出。
> 因此 PDF 排版必须**高度可读、可直接投递**：A4、清晰分节、中文字体内嵌、不加水印。

### 4.2 硬规则

```
① 只改被勾选的条目；未勾选的原样保留（逐字保留，不许顺手润色）
② 每条改动必须回链 issue_id，PDF/JSON 里能对上
③ 通过红线 ①②：新增名词、数字校验（同 §二）
④ 保结构：原简历的章节顺序、公司/时间/职位一字不改（只允许改职责描述句）
⑤ 输出：docx 输入 → `<原名>_修改版.docx`；PDF 输入 → `<原名>_修改版.pdf`；**原文件绝不覆盖**
⑥ 必带「未采用说明」：哪几条建议没改、为什么（如「缺真实数据，需你自己补」）
⑦ **版式策略（v1.3 核心）：尽量与用户上传保持一致**
   - **docx 输入** → 原地替换段落文字：只改被勾选的那几句，其余 run / 样式 / 表格 / 图片
     / 页边距 / 页面方向 / 页眉页脚 全部保留（见 §4.4）
   - **PDF 输入** → 无法保留版式（PDF 不可编辑），输出重排后的单栏 PDF，
     并在报告里明确写「原文件是 PDF，版式已重排；如需保留原版式请上传 Word 版」
   - ✗ 不许为了「好看」统一重排 docx；✗ 不许引入原文件没有的字体
⑧ **意见 PDF 与改后简历必须同时产出**；「本次修改说明」（issue_id / 原句 → 新句 / 理由 /
   未采用项）放进**意见报告 PDF 的「智能修改」章节 + JSON 的 adaptations**，
   ✗ 不许写进简历文件本体（会污染用户版式、也会被误发给 HR）
```

### 4.3 不许做的事

```
✗ 不许改公司名、学校名、时间、职位名
✗ 不许把两条经历合并成一条（会丢时间线）
✗ 不许删除整段经历（可以建议调序，不许静默删）
✗ 不许在改写里加入原简历没有的项目名
```

---

### 4.4 docx 版式保留的技术方案（v1.3 新增）

```
① 定位：遍历 body 段落 **以及所有表格单元格内的段落**，
   按「去空白后的文本 == issue.original_text」精确匹配；匹配不到 → 该条跳过并记 skipped
② 替换走 run 级，不整段重写：
   · 目标句只在一个 run 内 → 直接改该 run 的 text（格式天然保留）
   · 跨多个 run → 新文本写入第一个 run，其余 run 的 text 置空（不删 run，保留格式对象）
   · 新旧长度不同是常态，允许；不许动 run 的 font/size/bold/italic/color
③ 段落级属性（style / 对齐 / 缩进 / 行距 / 编号）一律不动
④ 只改文本，不许增删段落、不许合并或拆分段落（否则版式会挪位）
⑤ 输出：`<原名>_修改版.docx`，写入 reports/；**原文件绝不覆盖**
⑥ 兼容性红线：以下情况不硬改，改为「建议手动改」并记 skipped
   - 文本框 / 艺术字 / SmartArt 里的文字（python-docx 取不到 run）
   - 目标句在页眉页脚里
   - 文档有未接受的修订痕迹（track changes）
⑦ 验收断言：抽 3 个未改段落 + 全部表格，样式名与 run.font 逐项与原件相等
```

## 五、岗位输入的组合规则（**岗位名必填，JD 选填**）

### 5.0 三种组合

| 岗位名 | JD 文本 | 走的路径 | `profile.source` | 准确性 |
|---|---|---|---|---|
| ✓ | ✓ | 用真实 JD 解析（S1 链路），岗位名只作为报告标题 | `user_jd` | 最准 |
| ✓ | ✗ | 按岗位名生成画像草案 → **用户确认** → 再分析 | `inferred` | 推测，需声明 |
| ✗ | ✓ | 允许（从 JD 里抽 title），但提示「建议补岗位名」| `user_jd` | 准 |
| ✗ | ✗ | **拒绝**：返回 422「请至少填写岗位名称」| — | — |

**优先级**：有 JD 就用 JD（绝不因为用户填了岗位名而忽略 JD）；
岗位名与 JD 里的 title 不一致时，以 JD 的 title 为准，并在报告里记一条提示。

### 5.1 有 JD（推荐路径）

```
parse_job(jd_text) → JobInfo（source="user_jd"）
修改意见完全基于这份 JD，每条 jd_evidence 都能指到 JD 原文
```

### 5.2 只有岗位名（v1 允许，但必须诚实标注）

```
用户输入「Java 后端开发工程师」
  → 生成「岗位画像草案」：title + 6~10 条典型要求（must_have / responsibilities）
  → ⚠️ 界面/PDF 明确标注：**这是系统按岗位名推测的通用要求，不是岗位真实 JD**
  → 必须用户**点确认**后才进入下一步（未确认不许生成意见）
  → 报告 meta：source="inferred", confirmed=true, profile_version=...
```

**红线 ⑤ 的落地**：inferred 模式下 PDF 抬头必须出现一句
「本报告基于岗位画像（推测），非真实 JD；建议粘贴真实岗位要求后重新生成」。

**为什么允许**：用户常常只有一个岗位名（如面试邀请里只写了 title）；
但**必须让用户知道这是推测**，否则等于用假 JD 打分，属于欺骗。

## 六、输出契约（JSON，先定死再写代码）

```python
class ReviewIssue(BaseModel):
    id: str                    # R-001 递增
    category: str              # missing / weak_evidence / buried / noise / inconsistent
    severity: str              # high / medium / low
    location: str              # "工作经历 · 第 2 段"
    original_text: str         # 简历原句（必须能在原文检索到）
    suggested_text: str        # 建议改成什么（missing 类可空，改走 gain/risk_note）
    why: str                   # 为什么改（引用 JD 哪条 + 简历什么毛病）
    gain: str                  # 改完的好处（改前 → 改后 的具体对比）
    jd_evidence: str           # JD 原文依据（inferred 模式写「岗位画像：xxx」）
    risk_note: str             # 诚实提醒（数字/规模必须是真实数据）

class JobProfile(BaseModel):
    title: str
    source: str                # user_jd / inferred
    confirmed: bool
    must_have: list[str]
    responsibilities: list[str]
    note: str                  # inferred 时的免责说明

class AdaptedText(BaseModel):
    issue_id: str
    location: str
    before: str
    after: str
    added_terms: list[str]     # 改写里出现的新名词（须全部通过白名单校验）
    kept_numbers: list[str]    # 保留的数字（须全部在原文出现）

class RevisionReport(BaseModel):
    issues: list[ReviewIssue]          # 最多 12 条
    rejected_issues: list[dict]        # 被红线丢弃的（含原因，便于排查）
    profile: JobProfile
    score_before: int | None           # 复用评分模块的 total
    score_after_estimate: int | None   # 只改被采纳条目后重算（硬性+语义），LLM 部分标预估
    adaptations: list[AdaptedText]     # 仅「智能修改」时填充
    skipped: list[dict]                # 未采用的建议 + 原因
    meta: dict                         # 模型 / prompt 版本 / 成本 / 耗时 / 生成时间
```

### 6.2 内部结构（**不进对外 API**，供 M3 生成意见时引用；v1.4 新增）

```python
class KwCoverage(BaseModel):
    term: str                  # JD 里的必备词 / 职责关键词
    count_in_resume: int       # 在简历原文出现次数（大小写不敏感、去空白后统计）
    sections: list[str]        # 出现在哪些段落：技能 / 工作经历 / 教育 / 项目 / 其他
    from_must_have: bool       # 来自 JD 必备技能（True）还是职责关键词（False）

class DiagnosisFinding(BaseModel):
    code: str                  # 见 §6.3 枚举
    severity: str              # high / medium / low
    location: str              # 「工作经历 · 第 2 段」
    evidence: str              # 简历原文片段（**必须能在原文检索到**，否则丢弃）
    detail: str                # 一句人话说明问题

class DiagnosisReport(BaseModel):
    findings: list[DiagnosisFinding]        # 缺陷清单（诊断结果，不是修改意见）
    keyword_coverage: list[KwCoverage]      # ATS 关键词覆盖
    missing_keywords: list[str]             # JD 有、简历 0 次
    completeness: dict[str, bool]           # name / years / education / skills / contact
    meta: dict                              # 简历文件名字数 / 耗时（无模型成本 = 0）
```

### 6.2.1 提分预估结构（v1.7 新增，内部结构，供 M6 与 PDF「智能修改」章节使用）

```python
class ScoreDelta(BaseModel):
    before_total: int                  # 改前总分（来自评分模块，精确）
    after_total_estimate: int          # 改后预估总分
    before_parts: dict[str, int]       # {"hard":40,"semantic":21,"llm":25}
    after_parts: dict[str, int]        # llm 为「沿用原分」
    delta_parts: dict[str, int]        # after - before，逐项
    estimated_fields: list[str]        # ["llm"] —— 明确哪些项是估的
    covered_before: int                # 语义覆盖条数（改前）
    covered_after: int                 # 语义覆盖条数（改后）
    notes: list[str]                   # 人话解释：哪项为什么变，变了多少
    llm_tolerance: int = 2             # LLM 项预估误差 ±2
```

**重算规则（PRD §8.0.4 的落地，零模型）**
```
改后文本 = 原文 + 逐条 (before → after) 逐字替换
score_hard(new_text)      ← 零模型，精确
score_semantic(new_text)  ← 零模型，精确（本地 embedding + 重排）
LLM 30 分：不重跑，沿用 before 的 llm 分，estimated_fields=["llm"]
✗ 不许用「预期提升 X 分」这类营销话术；delta 为负必须如实显示
```

### 6.3 诊断缺陷枚举（**代码枚举，模型不许自创**）

| code | 判据（纯规则） | severity |
|---|---|---|
| `no_quantify` | 职责句里既没有数字也没有量级词（万/千/百/亿/倍/%）| medium |
| `weak_verb` | 职责句以「负责/参与/协助/配合」开头且无结果词（提升/降低/上线/交付/支撑）| low |
| `timeline_overlap` | 两段经历时间区间重叠 | high |
| `timeline_invalid` | 起止倒序，或结束年份晚于当前年 | high |
| `open_ended` | 出现「至今/现在/目前」，年限需人工确认 | medium |
| `relative_time` | 出现「去年/今年/最近/近期/应届」 | medium |
| `missing_section` | 缺 姓名 / 年限 / 学历 / 技能 / 联系方式 中任一项 | high |
| `skill_flat` | 技能段只有岗位方向词（后端/开发）而无具体技术 | medium |

## 七、PDF 结构（修改意见报告）

```
1 抬头      简历名 / 岗位名 / 模式标签（真实 JD 或 岗位画像推测）/ 生成时间
2 结论摘要  一句话诊断 + 3 条最该改的地方（不超过 3 条）+ 统计（高/中/低各几条、缺口几个）
3 逐条意见  每条一个卡片，固定四段：
            ① 原文（灰底，标注位置）
            ② 建议改为（高亮）
            ③ 为什么改（为什么 + JD 依据）
            ④ 改完的好处（改前 → 改后 对比）+ 风险提示
4 缺口清单  JD 要但简历没有的（诚实版：只列，不假装能补）
4.5 ATS 关键词覆盖（v1.6 新增）
            表格：关键词 / 出现次数 / 所在段落 / 状态（✓ 已覆盖 / ✗ 缺失）
            缺失项排在前面；数据来自 M1 的 DiagnosisReport.keyword_coverage
5 不建议改  明确告诉用户哪些改不动（如硬性年限不足），避免无效改稿
6 智能修改  若已生成：逐条 before/after 对比表 + 未采用说明
7 页脚      免责（AI 生成，须本人核对真实性）+ 审计小字（模型/prompt/成本/耗时）
```

### 7.1 渲染三态（v1.6 新增，**不许出现空白或与原文相同的「建议改为」**）

| 情况 | 「建议改为」栏印什么 |
|---|---|
| `suggested_text` 为空（missing 类）| 「（不可代写：如确有该经历，请在技能栏补充并说明使用场景）」|
| `before` 去空白 == `after` 去空白 | 「（此行需你补全：按实际在职月份/学历填写，系统不代拟）」|
| 正常 | 正常显示建议文本（高亮）|

**理由**：`missing` 类不写建议正文是 M3 的红线设计（缺的不能编）；
时间类意见模型不许编月份只能逐字保留。这两类若在 PDF 上留空或重复原文，
用户会以为系统没干活 —— 必须换成明确的人工动作指引。

### 7.2 「不建议改」清单的生成规则（代码确定性，不许模型发挥）

```
来源 = 硬性扣分 + 诊断里「靠措辞改不了」的条目
· hard.deductions type == years_short / years_unknown  → 「年限差距靠措辞改不动，需真实经历或换岗位」
· hard.deductions type == education / education_unknown → 「学历是硬门槛，可改的只有如实填写」
· diagnosis.findings code in (timeline_overlap, timeline_invalid, open_ended)
                                                        → 「时间线矛盾需本人核实，改写会变成造假」
· diagnosis.findings code == missing_section（年限/学历项）→ 「缺项只能本人补，系统不代拟」
每行四列：项 / 现状 / 为什么改不了 / 你能做什么
至少 1 行（缺项时）；无任何不可改项时印「本次没有发现改不动的问题」
```

排版要求沿用评分 PDF 的经验：`Paragraph` 自动换行、按列宽分档截断、每页页脚、
中文只走 `pdf_font.get_cjk_font()`、禁止静默降级 Helvetica。

### 7.3 第二份产出：修改后的简历（v1.3 修订；编号 v1.6 顺延）

**情况 A：docx 输入（推荐，版式不变）**

```
输出 = 用户原文件的结构，只有被勾选的那几句文字变了：
  字体/字号/加粗/颜色/对齐/缩进/行距/编号/表格/图片/页边距/页眉页脚 全部保留
  不加水印、不加页脚审计、不加修改说明页（保持可直接投递）
→ 修改说明去哪了：意见报告 PDF 的「智能修改」章节 + JSON 的 adaptations
```

**情况 B：PDF 输入（版式无法保留）**

```
输出 = 重排后的单栏简历 PDF：
  姓名居中加粗 / 求职意向=岗位名 / 教育经历 / 工作经历（公司·职位·时间 一行，职责 • 起头）/ 技能
  页脚审计小字（模型 / prompt 版本 / 成本 / 耗时 / 生成时间）
  报告里必须写明「原文件是 PDF，版式已重排；如需保留原版式请上传 Word 版」
```

**为什么 docx 不加审计页脚**：用户的简历是要投出去的，加任何非简历内容都会破坏版式与专业度。
审计信息是给用户和排查用的，放在意见报告里就够。
