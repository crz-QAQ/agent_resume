## 一、功能定义

### 1.1 一句话

输入「岗位名称 + （可选 JD）+ 简历」，输出一份**按结构分区的面试模拟题册**：题目来自你的真实简历与这份 JD 的交集和差距，每题给出考察点、依据原句、参考要点、加分点、翻车点和追问链。

### 1.2 为什么做这个

修改意见解决「简历写得对不对」，模拟面试解决「你守不守得住这张简历」。两者共用同一份事实基础：

```
评分     → 差在哪（硬性 / 语义 / LLM 三层）
修改意见 → 怎么改（改法 + 涨分 + 补能力）
模拟面试 → 改完敢不敢投（HR 会问什么、技术会挖到哪、追问到你答不出来为止）
```

如果模拟题不是从「你简历里真实写的东西 + 这份 JD 真实要求的东西」长出来的，那就只是通用题库，面试时一句都对不上。

### 1.3 输入

| 输入 | 必填 | 说明 |
|---|---|---|
| 岗位名称 | ✅ | 沿用 §五 的四组合规则（有 JD 时以 JD 为准） |
| JD 文本 | 选填 | 有 JD → `source=user_jd`；只有岗位名 → `source=inferred`，先出岗位画像并要用户确认 |
| 简历文件 | ✅ | docx / pdf，≤10MB；复用 `file_parser.extract_text` 与 `resume_parser` |
| 难度档 | 选填 | `junior` / `standard`（默认）/ `senior`，只影响追问深度与深度题比例，不影响题目来源 |

### 1.4 输出

**三条产出，三个形态**：
1. `InterviewPlan` JSON（接口返回，供网页渲染）—— 含每题的**参考答案**
2. PDF 题册（`app/interview_pdf.py`，复用 `pdf_kit`）—— 每题卡含参考答案（灰底、可折叠区）
3. `GradeReport` JSON + 评分 PDF（答完之后）—— 逐题得分、命中/漏掉的要点、建议、总分档位

> 评分是**本期范围**（v1.1 变更）：出题只是上半场，答完知道差在哪才是练习器。

### 1.5 题册结构（**这是本次的核心验收点，条数写死**）

```
HR 面          5~8 条   模型自由发挥（不写死条数，由岗位与简历决定；上下限硬校验）
技术面         10 条    固定配比，缺一条算未完成
  ├ 技术问答    6 条    考「你写的技术栈，到底多深」
  ├ 场景问答    2 条    考「给个真实业务问题，你怎么想」
  └ 项目自述    2 条    考「你说得清自己做的项目吗」
```

**为什么技术面必须是 6+2+2**：

| 分区 | 面试里真实占比 | 最能暴露什么 |
|---|---|---|
| 技术问答 6 | 一轮技术面 40~50% | 技术是背的还是做过的（追问两层就见底） |
| 场景问答 2 | 20~30% | 有没有业务判断力（FDE 岗位的核心） |
| 项目自述 2 | 20~30% | 简历里的项目是不是他本人做的（最容易被追问崩） |
| HR 面 5~8 | 单独一轮 | 稳定性、动机、薪资、离职原因 |

> 6/2/2 不是随便定的：技术问答少于 6 条覆盖不到「必备技能 + 项目细节 + 选型 + 排障」四类；场景少于 2 条测不出业务判断；项目自述必须 2 条，因为一份简历通常有 2 段以上经历，只问 1 条会被他挑最熟的那段答。

## 二、红线（违反即失败，代码校验，模型说了不算）

1. **不许编造简历里没有的经历当题干**
   题干里出现的公司名、项目名、时间段，必须在简历原文里找得到（复用 `guard_revision.find_original`）。找不到 → 该题丢弃。
   反例：「你在某某银行做的信贷中台，最大的技术难点是什么？」——简历里没有这家银行，等于让用户为虚构经历圆谎。

2. **不许把简历没写的技术当作「你已经会」来问**
   可以问「如果让你上 Kafka，你会怎么设计」，但题干必须带标记：`（简历未提及，考察迁移能力）`。
   简历里没有的技能被当成已有技能提问 → 判失败。

3. **参考答案分两层：要点 + 示范作答，且示范必须建立在你的真实事实上**
   - `answer_points`（3~6 条要点短句，每条 ≤30 字）：评分维度，用来自查「说到没说到」，禁止整段成文
   - `reference_answer`（120~300 字示范作答）：给一个「像样的答法」长什么样，但必须满足：
     ① 只能引用简历/JD 里已有的事实、技术、数字、项目名（复用 `find_original` + `new_numbers` 校验）
     ② 不许出现简历里没有的量化成果（「提升了 40%」这种必须原文有，否则删掉换成「（此处填你的真实数字）」）
     ③ PDF 与网页上必须标「**示范作答，不是标准答案；先自己说完再看**」
     ④ 禁止出现「标准答案」「必过话术」等字样
   理由：没有参考答案，用户不知道「答到什么程度算够」；给了整段范文又可背 —— 所以给示范 + 强制标注 + 强制可追溯。

4. **每题必须可追溯依据**
   `basis` 必须指向 JD 原句或简历原句，且用 `find_original` 校验通过。指不到 → 丢弃并计入 `rejected`。

5. **不许承诺结果**
   题册与 PDF 里禁止出现「答完必过」「通过率」「押题命中」等表述；难度只允许 1~3 星（`difficulty`），不许写百分比。

6. **不许出现简历/JD 都没有的数字与专名**
   复用 `guard_revision.new_numbers` / `new_tech_terms`：题干里新增的数字或技术名词，必须能在这两份原文里找到。

7. **题目不许互相重复**
   归一化后（去标点、去「请/谈谈/说说」等前缀）相似度 ≥0.8 视为重复，只保留一条；同一考点最多 2 条。

8. **评分不许「给面子」**
   要点没说到就是没说到：`hit_points` 必须逐条列出命中/未命中，不许把「答得挺长」算成命中；
   一致性冲突（答案里出现简历没有的技术/数字/项目）必须显式标红，不许静默加分；
   总分必须由公式算出（§7.2），禁止模型直接给总分。

## 三、生成规则

### 3.1 三段式：**结构由代码定，句子由模型写**（与 M1/M3 同构）

```
① N1 骨架（零模型）    决定「考什么」：分区配额、考点类别、每题的依据原句、难度基准
② N2 生成（模型）      只负责把骨架写成一句像样的题干 + 参考要点 + 加分点 + 翻车点 + 追问
③ N2 校验（零模型）    红线 1~7 全部过一遍，不过就丢弃；配额不足时用模板题兜底注入
```

**为什么不让模型一次生成整份题册**：模型会均匀地出一些「通用好题」，而你的真实短板（比如「知识库」「工作流」两个必备技能为零）它根本不知道。骨架必须由代码从评分产物里算出来。

### 3.2 骨架怎么算（N1，纯规则）

**输入端全部复用已有产物**：

| 来源 | 取出什么 | 用途 |
|---|---|---|
| `job.must_have` + `resume.skills` | 交集 / 仅在 JD / 仅在简历 | 决定技术问答的命运题 |
| `scoring_rules.score_hard.deductions` | `missing_skill` 列表 | 至少 1 条技术问答必须落在这上面；回答「你怎么补」进追问链 |
| `scoring_semantic.per_item` | `covered=False` 的职责 | 转成场景问答（「如果这活交给你，你怎么做」） |
| `scoring_llm` 子项分 | 技术深度 / 业务场景 / 成果 三档 | 决定 `difficulty` 与追问层数：某子项 <60% 满分 → 该维度多出 1 条且追问 +1 层 |
| `resume_diagnose.findings` | `weak_verb` / `no_quantify` | 转成「讲结果」类追问（项目自述必问量化） |
| `uplift_plan` | `blocked=False` 的条目 | 追问链第 2 层：「这个缺口你打算怎么补」 |
| 简历原文 | 项目段落（含时间、项目名） | **2 条项目自述必须点名真实项目**，不许说「挑一个你最熟的项目」 |

**六条技术问答的考点分配（硬性）**：

| # | 考点 code | 考什么 | 依据来源 |
|---|---|---|---|
| 1 | `tech_depth` | 必备技能里最核心那一项的深度 | `must_have` ∩ 简历 skills |
| 2 | `tech_gap` | JD 要、简历没有的那项（标记「简历未提及」） | `missing_skill` |
| 3 | `impl_detail` | 简历里写的一个具体实现细节 | 简历项目段原句 |
| 4 | `tradeoff` | 选型/取舍（为什么不用另一个） | 简历技术栈 ∩ JD |
| 5 | `debug` | 出故障怎么定位（生产视角） | 简历技术栈 |
| 6 | `growth` | 最近学的东西落地到什么程度 | `nice_to_have` 或简历「个人优势」 |

**两条场景问答（硬性）**：
- `scenario_design`：来自一条 `covered=False` 的 JD 职责（「这活交给你，你怎么做」）
- `scenario_risk`：来自 `missing_skill` 或 `years_short`（「客户现场发现做不到，你怎么说」）

**两条项目自述（硬性：由系统随机抽，不由用户挑）**
- code：`project_random_1`、`project_random_2`
- **抽取方式**：从简历里能定位到「项目名 + 时间」的段落中**随机抽 2 段**，不按「最量化/最杂」排序
- 随机种子固定可复现：`seed = sha256(plan_id)[:16]`，写进 `meta.project_seed`
  （同一次题册永远抽到同一对项目，便于复盘；换一次出题就换一对，避免只练熟的两段）
- 硬约束：两段**必须来自不同项目**（项目名归一后不同）、时间段不重叠；
  若只能抽到 1 段 → 第 2 条退化为「你最想讲的一段经历」（`flag="未定位到第二段项目"`）
- 每条的 `basis` 必须包含该项目的真实原名与时间

**为什么改成随机**（2026-11-16 拍板）：按「最量化/最杂」排序，等于每次都考他最会讲的那两段，
练三遍就背下来；随机抽会逼他讲不熟的段，这才接近真面试（面试官随手翻一页就问你）。
代价是偶尔抽到弱项目 —— 那正是需要提前准备的。

**HR 面（5~8 条，模型自由发挥但受约束）**：
- 必含：离职/转岗动机、薪资期望（对齐 `期望薪资` 原句）、职业规划、团队协作冲突
- **跨行必问（条件触发，`category=career_switch`）**：只要**检测到跨行**，必须有一条
  「为什么从 A 转 B」，且必须指向简历里的真实职位/意向原句
  ```
  跨行判定（任一成立即算跨行，纯规则）：
    ① 简历「求职意向/期望岗位」所在岗位族 ≠ 目标岗位族（用 job_profile.match_family 比）
    ② 最近一段经历的职位名所在族 ≠ 目标岗位族
    ③ 简历技能族与 JD 必备技能族完全不重叠，且目标族在简历中出现 0 次
  同族（比如 Go 后端 → 后端）→ 不出这条，避免无效题
  判定不出来（抽不到职位名）→ 不出，并在 meta.warnings 记「未能判定是否跨行」
  ```
  依据：他的简历写「求职意向：Golang 开发工程师」，目标岗是「AI 业务落地专家」→ 必然触发
- 若简历里 `years < required_years_min`：必加「年限不足你怎么补」
- 若简历有 `open_ended` 或 `timeline_overlap` 缺陷：必加「这段时间在做什么」（不许替他解释，只出题）
- 上限 8 条；超过部分按「与岗位相关度」丢弃

### 3.3 题目字段契约（逐字段校验）

| 字段 | 类型 | 约束 |
|---|---|---|
| `id` | str | `Q-HR-01` / `Q-T-01` / `Q-S-01` / `Q-P-01` 前缀固定，服务端生成，模型不得输出 |
| `part` | enum | `hr` / `tech` / `scenario` / `project` |
| `category` | enum | 见 §3.2 的 code 表，模型不得自创 |
| `difficulty` | int | 1~3 |
| `question` | str | 20~120 字，必须含疑问语气；禁止直接抄 JD 原句（复用 JD 雷同闸门，阈值 0.7） |
| `assesses` | str | 这一题考什么能力，≤20 字 |
| `basis` | str | JD 或简历原句，必须 `find_original` 通过 |
| `basis_source` | enum | `jd` / `resume` |
| `answer_points` | list[str] | 3~6 条，每条 ≤30 字，禁止成段（评分维度） |
| `reference_answer` | str | 120~300 字示范作答；只能引用原文事实与数字；PDF/网页强制标「示范，非标准答案」 |
| `bonus` | list[str] | 1~3 条加分点 |
| `pitfalls` | list[str] | 1~3 条翻车点（他容易答错的点，来自简历缺陷与缺口） |
| `follow_ups` | list[str] | 1~3 条追问（`standard` 2 条，`senior` 3 条） |
| `flag` | str? | 仅 `tech_gap` 类为 `简历未提及，考察迁移能力` |

### 3.4 降级与兜底

| 情况 | 行为 |
|---|---|
| 模型全挂（`fallback` 三家都失败） | `status="failed"`，不返回半成品；接口 503 |
| 模型输出条数不足（如技术问答只给 4 条） | 用**模板题**补齐到 6/2/2，模板题 `source="injected"`，PDF 里标「（模板题：按你需要重点准备）」 |
| 红线丢弃后某分区为空 | 该分区全部用模板题填充，并在 `meta.warnings` 里写明丢弃原因统计 |
| 简历里项目段抽不到（如纯 PDF 单栏无小标题） | 项目自述退化为「请挑一段你最有把握的经历」，`flag="未定位到项目段"` |
| 岗位画像未确认（只有岗位名） | 沿用 M2：抛 `ProfileNotConfirmed`，前端要求确认后才生成 |

### 4.2 答题与评分契约（v1.1 新增）

```json
// 请求：POST /interview/grade
{
  "plan_id": "32位hex",
  "answers": [
    { "id": "Q-T-01", "answer": "……用户自己答的原文，≤2000 字……" },
    { "id": "Q-P-01", "answer": "……" }
  ]
}

// 响应：GradeReport
{
  "plan_id": "32位hex",
  "items": [
    {
      "id": "Q-T-01",
      "part": "tech",
      "score": 7,                      // 0~10，公式见 §7.2
      "level": "可投",                  // 危险(<5) | 需练(5~6) | 可投(7~8) | 强(9~10)
      "hit_points": ["说清了技术选型理由", "提到了 QPS 量级"],
      "miss_points": ["没讲踩过的坑", "缺少结果数字"],
      "consistency": { "ok": true, "issues": [] },   // 答案与简历冲突时 ok=false + issues
      "depth": 1,                       // 0 结论层 / 1 做法层 / 2 取舍踩坑层
      "next_step": "把「为什么不用 X」补一句，面试官必追"
    }
  ],
  "total": { "tech": 63, "hr_hit_rate": 0.6, "band": "需练" },
  "advice": ["技术问答的坑全在「结果没数字」，先把 3 个项目各补 1 个数字", "……"],
  "meta": { "status": "ok", "model": null, "cost_yuan": 0, "duration_ms": 412,
            "estimated_fields": [], "prompt_version": "grade_v1.0" },
  "pdf_url": "/interview/file/<grade_id>/grade"
}
```

**关键约定**
- 评分**默认零模型**（要点命中走本地 embedding + 规则），`meta.cost_yuan = 0`；
  仅当用户勾选「要深度点评」时才调 1 次模型，且该维度标 `estimated_fields=["depth"]`
- `total.tech` = 技术面 10 题得分之和（满分 100）；HR 面不计入总分，只报「要点命中率」
- 档位用词：危险 / 需练 / 可投 / 强 —— 不许出现「通过率」「必过」

**内部结构不进 API**：`InterviewSkeleton`（N1 产物：考点槽位列表）只活在后端，避免模型与前端各写一套。

## 五、PDF 结构（题册，`app/interview_pdf.py`）

| 章 | 内容 | 要点 |
|---|---|---|
| 抬头 | 岗位名、来源（真实 JD / 岗位画像推测）、难度档、生成时间 | 画像来源必须红字标注「非真实 JD」 |

## 七、答题与评分（v1.1 新增）

### 7.1 交互流程

```
出题（N2/N4）→ 网页第三 tab 显示 10+ 题 →
用户逐题作答（可只答部分；未答的题不给分，但不算 0 而是「未作答」）→
点「交卷评分」→ POST /interview/grade → 逐题得分 + 总分 + 建议 + 评分 PDF
```

**允许部分作答**：只答 3 题也能评分，`total.answered = 3`，档位按「已答题均分」给，并明确写「按已答 3 题计算」。

### 7.2 每题 10 分的算法（**公式写进代码注释，默认零模型**）

| 维度 | 分 | 怎么算（全部可复算） |
|---|---|---|
| 要点覆盖 | 0~5 | `round(5 × 命中要点数 / 要点总数)`；命中判定 = 本地 embedding 余弦 ≥0.55 **或**关键短语包含（都要，取或） |
| 结构与量化 | 0~2 | 有「背景/角色/做法/结果」四要素中 ≥3 → +1；答句里出现数字或量化词（提升/降低/耗时/占比/QPS）→ +1 |
| 深度 | 0~2 | 只给结论 → 0；讲了做法 → 1；讲了取舍或踩过的坑（「当时也试过…」「因为我们放弃了…」信号）→ 2 |
| 一致性 | 0~1 | 答案里出现简历没有的技术/数字/项目 → 0 并记 `consistency.issues`；无冲突 → 1 |

```
单题得分 = 要点覆盖 + 结构与量化 + 深度 + 一致性        // 0~10
技术面总分 = Σ 10 题得分                               // 0~100
档位：  <50 危险 ｜ 50~69 需练 ｜ 70~84 可投 ｜ ≥85 强
```

**为什么要点覆盖只占 5 分**：真实面试里「说全要点」远不如「答得有深度」值钱；但要点是**唯一客观可复算**的部分，所以给它一半权重，其余靠规则近似。

### 7.3 深度与一致性的判定（规则优先，模型可选）

- **深度信号词**（写进常量 `DEPTH_SIGNALS`）：因为、当时也、试过、放弃了、取舍、踩坑、回滚、故障、复盘、监控告警
- **一致性检查**（复用 M0 三把刀）：`new_tech_terms(answer)` 与 `new_numbers(answer)` 相对「简历 ∪ JD」求差集；
  差集非空 → 不是判错，而是标 `consistency.issues` + 「这个词你简历里没有，面试官会追问」。
  **理由**：面试时说简历里没有的技术不算违规，但一定是高风险点，必须提示。
- **LLM 深度点评（可选，默认关）**：勾选后调 1 次模型，只产出「深度」这一维的 0~2 分与一句点评，标 `estimated`。

### 7.4 评分结果的诚实边界

```
① 分数是「按你要点算的」，不等于面试官给分
② 要点是本系统从 JD/简历推的，可能漏掉面试官关心的东西
③ 未作答的题不给分，也不判 0（避免虚低）
④ 不许因为「答得多」加分：字数只用于深度信号词判断，不直接换分
```

## 八、答题状态机与多形态接入（v1.2 新增）

### 8.1 问题：本项目有五种交付形态，只有一种有浏览器

```
① 本地部署（uvicorn + 网页）        有浏览器会话 → 可以用前端状态
② HTTP API（curl / Postman / 别人的系统调用）   无会话、无 cookie、无前端
③ MCP 工具（agent 调用）                        一次一个工具调用，没人替他记「刚答了哪题」
④ Skill（单文件脚本，stdin/stdout 一次性）       进程结束状态就没了
⑤ 单页网页（静态文件，无后端状态）               —— 见 8.6
```

**所以答题状态不能放在浏览器里，必须放在服务端，且用 `plan_id` 作为唯一凭据。**

### 8.2 状态机（服务端唯一真相）

```
        POST /interview/plan
                 │
                 ▼
   ┌──────── plan_created ────────┐
   │  plan 已生成，answers 为空    │
   └───────────┬──────────────────┘
               │ POST /interview/answer（0..n 次，可乱序、可只答一部分）
               ▼
        answering（answered = k / 10）
               │ POST /interview/grade（随时可交卷，k 可以 < 10）
               ▼
            graded ──── 再 PUT /interview/answer 改答案 → 回到 answering（grade 作废重算）
```

**同时只允许一个进行中的答题会话**：一个 `plan_id` 对应一份答案表，重复提交同一题 = 覆盖（last-write-wins）。

### 8.3 `plan_id` 就是能力令牌（v1 无鉴权下的唯一防线）

```
· 32 位 hex 随机（secrets.token_hex(16)），不可枚举，≥128 bit
· 持有 plan_id 才能：读题册、追加答案、交卷、下载 PDF
· plan_id 不下发到任何日志；响应里不出现简历原文
· TTL 30 分钟（与 report_store 一致）；过期 → 404，客户端需重新出题
· 同一 plan_id 被 200 次以上请求 → 429（防扫描）
```

**明确写进限制**：v1 是**单实例内存态**。多副本部署时答题会话不共享，需要 sticky session 或外部存储；这是已知限制，不在这期解决（见 §九 限制）。

### 8.4 三个新接口（API 形态的核心）

```http
### ① 出题（已存在）→ 返回 plan_id + 全部题目（含参考答案）
POST /interview/plan
  multipart: file, job_title, jd_text?, difficulty?
  200 → InterviewPlan  （含 plan_id、parts、pdf_url、next_action）

### ② 增量作答（新增，幂等覆盖）
POST /interview/answer
  application/json:
  {
    "plan_id": "…hex…",
    "answers": [ { "id": "Q-T-01", "answer": "…≤2000字…" } ]
  }
  200 → {
    "plan_id": "…", "answered": 3, "total": 10, "missing_ids": ["Q-T-02", …],
    "next_action": { "type": "answer_remaining",   // answer_remaining | can_grade
                     "suggest": ["Q-T-02", "Q-S-01"],
                     "hint": "还有 7 题未答；也可以现在就交卷（已答 3 题按均分计）" }
  }
  404 plan 不存在或过期 ｜ 413 单题 >2000 字或总量 >20000 字 ｜ 422 id 不在本 plan 里

### ③ 交卷评分（已存在，语义扩展）
POST /interview/grade
  {
    "plan_id": "…hex…",
    "answers": [ …可选，用于「一次性提交并评分」的无状态调用… ],
    "include_answer_text": false        // 评分 PDF 是否带我的答案原文，默认 false
  }
  200 → GradeReport（含 next_action: {type:"done"}）
  422 一题都没答（answered == 0） ｜ 404 plan 过期
```

**关键设计：`/interview/grade` 允许自带 answers**
- 有状态客户端：先 `/answer` 累加，最后只传 `plan_id` 交卷
- 无状态客户端（单文件 Skill、一次性脚本）：**不调 `/answer`，直接把全部答案塞进 `/grade`**，一次调用完成
- 两者结果完全一致（幂等）：评分是纯函数 `f(plan, answers)`

### 8.5 `next_action`：给 agent 用的状态提示（MCP / Skill 的关键）

每个响应都带 `next_action`，让「不会记状态」的调用方也能自驱：

| 当前状态 | `next_action.type` | 调用方该做什么 |
|---|---|---|
| 刚出题 | `answer` | 逐题作答后 POST `/interview/answer` |
| 已答部分 | `answer_remaining` | 继续答 `suggest` 里的题；也可以直接交卷 |
| 全部答完未评分 | `can_grade` | POST `/interview/grade` |
| 已评分 | `done` | 结束；要看报告就下载 `pdf_url` |
| plan 过期 | HTTP 404 + `next_action.type="restart"` | 重新出题 |

**为什么不返回「第几题」这类游标**：agent 可能跳过、乱序、重答，游标会和真实答案表打架。返回「还缺哪几个 id」是幂等的。

### 8.6 三种无浏览器形态的接法

| 形态 | 接法 | 状态在哪 |
|---|---|---|
| **HTTP API** | curl 三连：`/plan` → 多次 `/answer` → `/grade`；或 `/plan` → `/grade`（一次带全部答案） | 服务端内存（plan_id） |
| **MCP 工具** | 三个工具：`interview_plan`（出题）、`interview_answer`（追加答案）、`interview_grade`（交卷）。每个工具返回结果里原样带回 `next_action`，agent 照着走 | 服务端内存；MCP 只传 plan_id |
| **Skill / 单文件脚本** | 一次调用：读 stdin 的 `{resume_path | resume_b64, job_title, jd_text?, answers?}` → 无 answers 输出题册 JSON，有 answers 直接输出 GradeReport | 无状态，进程内算完即走 |
| **单页网页（静态）** | 页面不含状态，答案存在页面内存里；交卷时把 `plan_id + answers` 一次 POST `/grade`。页面本身不写 localStorage | 页面内存 + 服务端 plan |

**MCP 三工具的最小契约**
```
interview_plan(file_path | file_b64, job_title, jd_text?, difficulty?) -> {plan_id, parts, pdf_url, next_action}
interview_answer(plan_id, [{id, answer}])                              -> {answered, missing_ids, next_action}
interview_grade(plan_id, answers? | null, include_answer_text?)        -> {items, total, advice, pdf_url, next_action}
```

### 8.7 答案的存储与隐私（**比题册更敏感**）

```
① 答案**不落盘**：只存在服务端进程内存（dict[plan_id] -> answers），随 plan TTL 一起过期
② 不写日志：答案文本禁止进 logging / traceback / PDF 元数据
③ 评分 PDF 默认**不含答案原文**（include_answer_text=false 时只印分数与命中要点）
④ 交卷后答案保留到 plan 过期（30 分钟），方便改答案重算；过期即销毁
⑤ 响应体永不含简历原文；`hit_points` 只引用 plan 里已有的要点，不回显简历
⑥ 已知限制（写进 README）：单实例内存态 → 重启丢失、多副本不共享
```

### 8.8 为什么不做「登录 + 历史记录」

```
① v1 无鉴权是既定边界（README 已写明「不要直接暴露到公网」），加登录会把范围扩大到账号体系
② 面试练习是短周期行为：30 分钟够答完 10 题
③ 需要留档的，下载评分 PDF 即可（用户自己保存）
④ 真要历史记录，属于 v2 的「多次对比」功能，届时再引入存储设计
```

| 可追溯 | 每题 `basis` 经 `find_original` 校验通过率 100%；`rejected` 每条带原因 |
| 红线 | 编造公司名 / 编造数字 / 抄 JD 原句 / 把未提及技能当已会 —— 四类各有一条用例必须被拦 |
| 项目自述 | 2 条题干必须含简历里真实项目名与时间 |
| 成本 | 单次 ≤0.02 元（约 3 次模型调用：JD 抽取 + 出题 + 可选题干润色） |
| 性能 | 端到端 ≤45 秒（含 JD 抽取与打分复用） |
| 降级 | 模型全挂 → 503；条数不足 → 模板补齐且 `source=injected`；画像未确认 → 422 |
| PDF | 七章齐全、6~9 页、每题不跨页、页脚有审计行 |
| 参考答案 | 每题都有 `reference_answer`；抽 3 条用 `find_original` 校验其中事实可追溯；PDF 上带「示范，不是标准答案」 |
| 评分·公式 | 手算一份 3 题答案，逐题与代码输出对得上（要点 5 + 结构 2 + 深度 2 + 一致性 1） |
| 评分·确定性 | 同一份答案连跑三次，逐题得分与总分完全一致；`cost_yuan` 恒 0 |
| 评分·边界 | 空答案 → 未作答不计分；答非所问（长但与要点全不沾）→ 要点覆盖 0，不许因字数加分 |
| 评分·一致性 | 答案里编一个简历没有的技术/数字 → `consistency.ok=false` 且扣该 1 分并列出 |
| 项目随机 | 同一 `plan_id` 两次生成抽出同一对项目（seed 可复现）；两段项目名不同、时间段不重叠；只抽到 1 段时第 2 条带 `flag` |
| 跨行触发 | 他的真简历（Golang 意向）× FDE 岗 → 必出 `career_switch` 一条；Go 后端简历 × Go 后端岗 → 不出 |
| 多形态·等价性 | 同一份答案，`/answer`×N + `/grade` 与 `/grade` 一次带全部答案，逐题得分完全一致 |
| 多形态·状态 | 乱序作答、重复作答（覆盖）、部分作答均正确；`next_action` 五种状态齐全且可驱动 agent |
| 多形态·过期 | 过期 plan_id → 404 + `next_action.type=restart`；不得返回半份数据 |
| 答案隐私 | 答案不落盘（重启后 plan 消失）、不进日志、评分 PDF 默认不含答案原文 |
| 隐私 | 响应不含简历全文；PDF 只含题目与要点，不含简历原文 |

### 9.1 已知限制（写进 README，不藏）

```
① 答题状态在服务端内存：重启进程 → 进行中的答题全部失效（重新出题即可）
② 多副本部署不共享答题会话：要么 sticky session，要么等 v2 外部存储
③ 无鉴权：plan_id 即权限，请勿把服务直接暴露到公网
④ 一次只支持一份进行中的题册：同一 plan_id 反复出题会覆盖旧答案
```
