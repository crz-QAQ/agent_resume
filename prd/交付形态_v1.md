## 一、三种形态的边界（同一个核心，三条出口）

```
核心层（已完成，纯函数、不依赖 FastAPI）
  app/resume_parser.py  app/job_parser.py  app/scoring_rules.py
  app/scoring_semantic.py  app/scoring_llm.py  app/match_report.py  app/report_pdf.py
        │
        ├─ ① 本地部署   docker compose up  → 浏览器 Swagger（D1 已完成，镜像 726MB）
        ├─ ② API 调用   POST /match/score + GET /match/report/{id}（S7b 已完成）
        └─ ③ Skill 给 agent  ← 本文定义（D3 待做）
```

**一条铁律**：三种形态**共用同一套打分逻辑**，任何形态都不许复制/改写算法。
③ 的脚本只能「调用」核心层或 API，不许自己算分。

## 二、③ Skill 的两个子形态（必须分开，用途完全不同）

| 子形态 | 名字 | 谁用 | 解决什么问题 |
|---|---|---|---|
| **A 能力型** | `resume-job-matcher` | 一个 agent 需要「帮人给简历打分」时 | 让它**会调用**：输入简历文件 + JD，输出 100 分报告 + PDF |
| **B 方法论型** | `match-scoring-design` | 一个 agent/工程师要**做类似系统**时 | 让它**学会设计**：为什么 40/30/30、为什么未知≠0、为什么余弦要加重排 |

> 分开的理由：A 回答「怎么用」，B 回答「为什么这么做」。
> 面试官问「你怎么保证打分可信」答的是 B；别人用你仓库要的是 A。

## 三、A 能力型 skill 的契约

### 3.1 文件结构（放在仓库 `skills/` 下，便于别人复制到自己 agent）

```
skills/resume-job-matcher/
  SKILL.md            触发条件、前置条件、两种调用方式、输出的解读、坑
  scripts/score.py    单文件 CLI：--local（直接 import 核心层）/ --api（打 HTTP）
```

### 3.2 SKILL.md 必须说明的两条调用路径

```
路径 1（推荐给 agent，零依赖服务）：--local
  python skills/resume-job-matcher/scripts/score.py --local \
      --resume <简历.pdf|docx> --jd <jd.txt> [--out <报告.pdf>]
  内部：import app.match_pipeline.run_match + render_report（同一进程，无需起服务）

路径 2（服务已在跑）：--api
  python .../score.py --api --resume <文件> --jd <jd.txt> --base-url http://127.0.0.1:8000
  内部：POST /match/score → GET /match/report/{id}
```

两条路径的输出必须**逐字段一致**（同一份输入 → 同样 total、同样 deductions）。

### 3.3 输出契约（agent 要能直接读）

```
① 终端打印人读版：总分 / 档位 / 三项 / 扣分 / 缺口 / 前 3 条建议
② --json 时输出机器读版：MatchReport 原样 JSON（字段名与 PRD §三 一致）
③ 生成 PDF 时打印绝对路径
退出码：0 成功；2 输入错误（文件不存在/格式不支持/扫描件/JD<20字）；3 服务不可用；4 内部错误
```

### 3.4 SKILL.md 必须写清的判据与解读

```
· 分档由代码算（≥85 高度匹配 / ≥70 匹配 / ≥55 勉强 / <55 不匹配），模型不许决定
· 每一个扣分必须能指到 JD 原文 + 简历原文；指不到就是 bug，不是"模型判断"
· years_unknown / education_unknown = 「简历没写」，不是「不合格」，报告里印 ? 不印 ✗
· status=needs_review 的常见原因：简历含「至今/去年」这类相对时间 → 年限要人工确认
· 语义分口径：余弦召回 top-3 + cross-encoder 精判，covered 由重排分 ≥0 决定
```

## 四、B 方法论型 skill 的契约

只写「怎么想」，不写「怎么调」。至少覆盖 6 个决策与各自的反例：

| 决策 | 反例（不这么做会怎样） |
|---|---|
| 100 分拆 40/30/30 | 单一总分不可解释，客户问「为什么 62 分」答不出 |
| 纯规则先于模型（S3 在 S5 前） | 模型飘的时候分不清是模型的锅还是汇总的锅 |
| 未知 ≠ 0（`years_unknown`） | 简历没写年限被当成 0 年 → 直接判不匹配，冤枉候选人 |
| 余弦召回 + 重排精判 | 单靠余弦，「负责数据库内核开发」对 Go 简历也得 0.711（真相关才 0.785）|
| 覆盖率进分母 | 6 条职责只对上 1 条也能拿 22/30 |
| 证据不可编造 + 空证据判 failed | 报告好看但无法追溯，等于把判断权交给模型 |

另含：如何用**假模型/monkeypatch** 验红线（不花钱验「模型不能决定档位」）、
为什么每块必须写「解决了什么」（防止做了一堆功能但没人知道消除了什么风险）。

## 八、④ MCP server（v1.1 新增，D4）

### 8.1 为什么做

③ 的 skill 是「agent 读了文档自己敲命令」；MCP 是「客户端直接把能力注册成工具」——
Claude Desktop / Cursor / 支持 MCP 的 IDE 里，模型不需要学命令行，直接调 `score_match`。

### 8.2 版本策略（**关键**）

```
mcp SDK 2.x 把 FastMCP 重命名为 MCPServer（from mcp.server.mcpserver import MCPServer），
2.x 与 1.x 不兼容。因此：
· requirements-mcp.txt 里必须写 `mcp>=2.0,<3`（不许写 mcp 不带版本）
· 代码里用 MCPServer，不用 FastMCP
· 文件顶部注释写明：升级到 3.x 前必须先读 migration guide
```

### 8.3 三个工具契约（名字与参数定死）

| 工具 | 参数 | 返回 |
|---|---|---|
| `parse_resume` | `resume_path: str` | `{name, years, skills, status, reasons, raw_chars}` —— 只解析，不打分（便宜） |
| `score_match` | `resume_path: str`, `jd_text: str` | `MatchReport` 原样 JSON（字段与打分 PRD §三 一致） |
| `make_report` | `resume_path: str`, `jd_text: str`, `out_path: str \| None` | `{report_path, total, verdict}` —— 打分 + 生成 PDF |

**共用 `app.match_pipeline.run_match`**，不许重写逻辑；`parse_resume` 只调 `resume_parser`。

### 8.4 传输与安全

```
· 默认 transport="stdio"（Claude Desktop 的标准接法），可选 "streamable-http"
· stdio 模式下不监听端口、不鉴权 → 天然只对本机客户端可见，这是 v1 的安全边界
· 工具内部读到路径必须校验：不存在/不支持 → 返回结构化错误（{"error": "..."}），不许抛裸 traceback
· 不许把简历原文写进工具返回值（只给结构化字段与统计），避免把隐私灌进模型上下文
```

### 8.5 判据

| # | 判据 |
|---|---|
| 1 | `mcp_server.py` 能启动（stdio），`list_tools` 返回 3 个工具且名字/参数与 8.3 一致 |
| 2 | 用官方 MCP 客户端（ClientSession）连上并**真实调用**三个工具全部成功 |
| 3 | `parse_resume` 返回里**不含**简历原文正文（只有 name/years/skills/status/raw_chars）|
| 4 | `score_match` 与 `score.py --local` 的 total 一致（同输入，允许 LLM ±2）|
| 5 | `make_report` 生成 PDF 且路径可读回中文 |
| 6 | 错误用例：文件不存在 → 结构化 error 字段，不崩进程 |
| 7 | README 补 Claude Desktop 的 `claude_desktop_config.json` 片段 |

### 8.6 不做

```
✗ 不做 OAuth / 多用户鉴权（stdio 本机模式不需要）
✗ 不做 resources/prompts（v1 只暴露 tools）
✗ 不把 MCP 打进 Docker 镜像（镜像里没有 display/客户端，本地开发用）
```

## 九、⑤ 单页网页（v1.2 新增，D5）

### 9.1 为什么做

Swagger 对工程师够用，对 HR / 业务方太重：要展开接口、选文件、粘贴、复制 report_id、再调第二个接口。
**单页网页是「非技术的人 30 秒能用完」的唯一形态**：上传 → 填 JD → 看分数 → 下载 PDF。

### 9.2 不引入任何构建链

```
· 单文件 app/static/index.html：原生 HTML + CSS + JS（fetch），不用 React/Vue/构建工具
· 不引外部 CDN（离线/内网可用），样式全部内联
· 由 FastAPI 直接返回该文件（FileResponse），URL = /ui
· 前端只调用已有接口：POST /match/score、GET /match/report/{report_id}，不新增后端接口
```

### 9.3 页面必须包含

| 区域 | 内容 |
|---|---|
| 抬头 | 标题 + 一句话说明 + **隐私提示**（简历敏感，勿上传到公共环境）|
| 输入区 | 简历文件选择（`.pdf,.docx`）+ JD 文本框（≥20 字，实时显示字数）|
| 按钮 | 「开始评分」；提交中禁用并显示「正在分析（10-30 秒）」|
| 结果区 | 总分大字 + 档位（颜色：≥85 绿 / ≥70 蓝 / ≥55 橙 / <55 红）+ 三项进度条 |
| 明细区 | 扣分表 / **语义覆盖明细**（✓✗?—）/ 缺失与待确认 / 建议（带来源标签）|
| 操作 | 「下载 PDF 报告」按钮（`/match/report/{id}`）|
| 状态 | `needs_review` 显示黄色提示条；`failed` 显示红色并说明原因 |

### 9.4 判据

| # | 判据 |
|---|---|
| 1 | `GET /ui` → 200，返回 HTML（含 `<form>`、文件 input、JD textarea）|
| 2 | 用真浏览器端到端：选 go_backend_resume.docx + 粘贴 JD → 点提交 → **页面出现总分与档位**（无需手抄 report_id）|
| 3 | 点「下载 PDF 报告」→ 触发 PDF 下载（或新窗口 200）|
| 4 | 扫描件 → 页面显示可读错误（不是白屏、不是 `[object Object]`）|
| 5 | JD < 20 字 → 前端直接拦下并提示，不发请求 |
| 6 | 页面无外部请求（无 CDN、无字体外链）：`grep -c "https://" app/static/index.html` 允许 0 个（注释里也不许）|
| 7 | 移动端宽度 375px 不横向滚动 |

### 9.5 安全与隐私

```
· 页面不存任何简历内容到 localStorage / cookie；刷新即清空
· 不做「历史记录」功能（v1）
· 服务仍只监听 127.0.0.1，v1 无鉴权 —— README 与页面均须写明不要暴露公网
```

### 9.6 不做

```
✗ 不做批量上传（v2）
✗ 不做账号/登录
✗ 不做前端路由与多页
✗ 不做简历预览（防止在页面上留存原文）
```
